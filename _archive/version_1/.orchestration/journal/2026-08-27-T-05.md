# T-05 — tags: create, attach, detach

15 PGlite tests, 3 browser tests. Tags are global to the user, attach many-to-many to
todos, and are created inline by typing a name onto a todo.

## The predicted friction did not appear

T-05 expected the cross-territory ownership question to sharpen — "which package owns the
join table?". It never came up. `todo_tag` is a table, and every table already lives in
`packages/db/src/schema/`, so ownership was decided before the question could be asked.
The queries over it went in `testbed/tags` because that is where the feature is; nothing
about the join table made that harder than a single-table feature.

Same pattern as T-03, whose predicted cross-package foreign key also dissolved. The schema
split is now two-for-two on removing a problem the territory model predicted. Worth
noticing that both predictions were written before that split existed.

## Real friction: the rule and the test database disagreed

`.claude/rules/database.md` forbids `db:generate` on a feature branch. `testing.ts` builds
the test database from committed migrations. Both are right, and together they meant the
new tables existed in `schema` and in no migration — so `createTestDatabase()` could not
see them, and the acceptance criterion "cascade direction asserted by a test" was
unreachable on the branch that wrote the cascade.

Neither obvious way out is acceptable. Committing a migration restores the three-way
conflict [[L-005]] exists to prevent — and the repository's own history does exactly that,
in T-02 and T-03, which is why the contradiction had stayed invisible. Hand-writing
`CREATE TABLE` in the test, as `examples/notes` legitimately does for a table with no
migration, makes a cascade test assert against DDL the test invented.

Fixed by deriving the delta: `applyPendingSchema()` diffs the newest committed snapshot
against the live schema with the same drizzle-kit `db:generate` uses. Nothing is written
to `drizzle/`. Guarded by a test that fails naming every missing column when the mechanism
is disabled — verified by disabling it. [[L-017]]

## Still open: the app itself cannot run on the branch

Closing the test half made the second half obvious and worse. `pnpm db:migrate` applies
committed migrations, so the real Postgres has no `tag` table either: the unit suite went
green while `/lists/[id]` would have 500'd, and the browser suite could not run until the
derived DDL was applied to the container by hand. The default gate skips e2e, so nothing
would have said so. Pulled as K-004.

## The optimistic path, again

The first browser run failed on a reload that raced its own in-flight action — the chip
rendered optimistically and the reload cancelled the save. The fix was an assertion rather
than a wait: an optimistic chip has no id yet, so its remove control is disabled until the
server answers, and waiting for it to enable is how the test distinguishes "rendered" from
"saved". [[L-015]] said only a browser catches this class of thing; it also catches tests
that only look like they check persistence.

## Ownership checks the foreign keys do not give you

`attachTag` verifies *both* ends belong to the caller. The foreign keys only prove the rows
exist, so without it a user could attach their own tag to a stranger's todo, or the
reverse, by guessing an id. Identical to the hole found on `createTodo` in T-03 — this is
now twice, on every table that references another, which suggests it belongs in
`examples/notes` rather than being rediscovered per feature.
