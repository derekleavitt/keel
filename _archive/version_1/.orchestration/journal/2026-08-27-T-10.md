# T-10 — sharing, and the end of row ownership

18 new unit tests, 5 browser tests, 46 browser tests total green. The first growth feature,
and the first one to invalidate an assumption the whole codebase rested on.

## What actually changed

Every query in every package said `eq(table.userId, userId)` — three identical `ownedBy`
helpers across three packages. That is correct exactly until two people touch one thing,
and then **"can I see this" stops being a property of the row**.

The answer: **the list is the authorization boundary.** Todos inherit access from their
list rather than carrying their own grants, so `todo.userId` now records who *created* a
todo and no longer decides who may see it. One ACL per list instead of one per row, and a
single grant covers everything inside.

`visibleVia()` and `editableVia()` are subqueries, not fetched id lists. The database
re-evaluates them per statement, so revoking takes effect on the next query — no cache to
invalidate, and no window where a stale list of ids is still trusted. There is a test for
exactly that.

The distinction that took the most thought: an **editor** may change what is *in* a list
but never who else can reach it. Without that, a grant quietly becomes the power to hand
the list to anyone, which is the usual way a sharing feature turns into a permissions hole.

## The refactor was safe because the tests were behavioural

All 140 existing unit tests passed unchanged after authorization moved from row-ownership
to list-ACL. They assert what a user can and cannot see, not how the scoping is built — so
they kept their meaning through a rewrite of the mechanism they were testing.

## Two failures, both mine, both self-inflicted earlier

**`db:sync` broke `db:migrate`.** `push` records nothing in the migration ledger, so
migrate later tried to re-apply migrations for tables that already existed. drizzle-kit
reported the cause as the literal string `undefined`, which sent me looking at the SQL —
valid, applied by hand fine — instead of at the ledger. Comparing the journal against
`drizzle.__drizzle_migrations` settled it in one step: seven entries, five applied.

I shipped `db:sync` in K-004 without saying it desynchronises the ledger. [[L-022]]

**And I swallowed the migrate output again** with `2>&1 || true`, for the second time —
T-04 was the first. The gate skips e2e by default, so a broken development database stays
invisible until a browser test hangs on a page that is throwing. Now called out in the rule.

## Ambiguous assertions, again

`getByText('can edit')` matched both the role `<option>` and the grantee row. Third time an
accessible-name collision has produced a red test that looked like an application bug.
The reliable fix each time has been to assert on something uniquely labelled — here, the
revoke button, which carries the grantee's email.
