# T-17 — recurring todos

A repeating series generates real todos, idempotently, in the user's timezone. 45 new unit
tests, 8 new browser tests; 73 browser tests green.

## The prediction was right about the topic and wrong about the difficulty

**Watch for** said "idempotency is the hard part and Keel says nothing about it. Expect a
lesson." It is only hard in the place the instinct puts it.

The instinct is a guard: before generating, look for an existing occurrence; skip if found.
That reads correctly and loses under exactly the conditions a job queue creates — two
workers sweep, both read, both find nothing, both insert. `SKIP LOCKED` stops two workers
claiming the same *job*, not two jobs racing on the same *row*.

The whole problem fits in a partial unique index on `(recurrence_rule_id, occurrence_date)`
with `on conflict do nothing`. No window, because there is no read-then-write. There is a
test that fires three concurrent generations and asserts the count. [[L-035]].

What the constraint does *not* cover is the second failure, and I nearly shipped a comment
claiming it did. Uniqueness stops duplicates; it does nothing about **resurrection** —
delete a generated todo and the next sweep finds no conflicting row and cheerfully recreates
it. That needs the `generated_through` watermark, so generation resumes from the day after
the last one instead of re-expanding the series. Two mechanisms, two failures, and
conflating them is how one of them silently stops working. I had written "a hint, not the
source of truth" in the schema and had to correct it.

## Where the real difficulty was: dates

Two silent bugs, each wrong only for some users or only on some days.

**Adding a day is not adding 86,400,000 milliseconds.** A local day across a DST boundary is
23 or 25 hours, so the addition lands on the wrong date and shifts everything after it —
twice a year, one hemisphere at a time. All arithmetic in `@keel/scheduling` happens in UTC,
which has no DST, over `YYYY-MM-DD` components.

**"Today" is a question about a place.** At `2026-03-08T06:30:00Z` it is the 8th in London
and the 7th in Denver. A generator using the server's date creates tomorrow's todo early for
everyone west of it. The zone is stored on the series and is **required with no default** —
a default would be the server's, and that bug is invisible to whoever deployed it, because
they are sitting next to the machine that happens to be right. The form sends
`Intl.DateTimeFormat().resolvedOptions().timeZone`, which costs nothing.

The tests cover `America/Denver` and `Australia/Sydney`, because a suite that only checks
March catches spring-forward and misses the zones that transition in April the other way.
[[L-036]].

## Series and instance, without a dialog

Every recurring-task feature eventually asks "edit this one, or all future?" — a question
users get wrong because it is asked after the fact. The answer here is structural: a rule is
a template, and what it produces are **ordinary todos** that point back at it.

| You edit… | What changes |
|---|---|
| a generated todo | that occurrence — it is just a todo |
| the rule | future occurrences only |
| delete a generated todo | that occurrence, permanently |
| delete the rule | nothing already generated |

No dialog, because the user chose which object they were acting on by what they clicked. And
because occurrences are real rows, sharing, tagging, filtering, search, the API and webhooks
all work on them with no changes at all — nothing in those features knows recurrence exists.

Deleting a series detaches its todos rather than cascading. Cascading would delete a month
of finished work because somebody stopped a reminder, which is not what anyone means. The
button says "Stop repeating" for the same reason.

## The capability came out generic

The date logic is `packages/scheduling` — pure functions, no database, no clock except the
one you pass. That split was not planned for elegance; it happened because the DST cases are
miserable to debug through a job queue and a database, and testing them as pure functions is
instant. 29 of the 45 new unit tests live there and run in 4ms.

It happens to be the reusable half — billing runs and digests need exactly this and none of
the todo-specific parts — which is the shape the task was asking for. Worth noting the
sequence: extracting it was a *testability* decision that turned out to be an architectural
one. That is usually the direction the arrow points.

## Against the graph prediction, fifth time

Recurrence touches the schema, two packages, the worker, the app and three existing
features. What found the problems was a failing assertion about weekday anchoring and
writing out the DST cases by hand. Still nothing a code graph would have contributed.
