# T-22 — rate limiting the public API

Per-address and per-key limits, shared across instances, differing by plan, with the allowance
reported on every response. 14 new unit tests, 4 new browser tests; gate 90s.

## The prediction ruled out the obvious implementation

**Watch for** called this "the first piece of genuinely shared runtime state. Nothing in Keel
addresses it." That is exactly the difficulty, and it disqualifies the in-memory counter
everyone reaches for first.

An in-memory counter is not a rate limit. It is the limit divided by however many instances
happen to be running — a number nobody chose, which changes when the platform scales, and
which no test on one machine will ever expose. Under serverless every cold start begins at
zero, so provoking new instances removes the limit entirely.

Postgres, then, and the whole operation in **one statement**: read, roll the window, increment.
Any read-then-write is two concurrent requests away from being wrong, and concurrent requests
are the entire situation a limiter exists for. The test that matters fires twenty simultaneous
attempts at a limit of five and asserts exactly five got through.

That is the third time this pattern has decided a design here — recurrence idempotency
([[L-035]]), billing event replay (T-21), now this. [[L-045]].

## Sliding window, because fixed windows lie

A fixed window lets a client spend its allowance at 0:59 and again at 1:00: twice the limit in
two seconds, every individual window compliant. Keeping the previous window's count and
weighting it by the remaining overlap removes the boundary burst for one extra integer. The
estimate smears a burst evenly across the previous window rather than being exact — the exact
version costs a row per request, which is a worse trade for a limiter.

## Limit before authenticating

The address check runs *before* the key is verified. A limit that only counts successful
requests leaves someone working through stolen or guessed keys completely unmetered, because
every one of their attempts fails auth. There is a browser test that hammers with a
well-formed but bogus key and asserts it eventually gets 429 rather than an endless supply of
401s.

## The limit that was too tight, found by the suite tripping over itself

The address limit started at 120/minute, and the browser suite exhausted it against itself —
every test runs from one address, and the rate-limit spec alone makes hundreds of requests.

The instinct is to call that a test artefact and exempt the tests. It is not: **that is the
same arithmetic an office behind one NAT does.** Shipped, it would have arrived as "the API
randomly returns 429 for our whole company". An address is a blunt identifier and its limit
should be generous; the per-credential limit is where the accounting belongs. Raised to
600/minute, with the reasoning written beside it.

The tests now send their own `x-forwarded-for` so they neither poison the rest of the suite
nor depend on how many ran before them — which is also a live demonstration of the caveat
`docs/api.md` now carries: that header is client-settable unless a proxy overwrites it, and
nothing the application can check will tell the difference. It is the operator's job, so it is
stated rather than pretended away.

## Keyed by credential, not by tenant

Two API keys in one organisation get separate budgets. Revoking a leaked key should also stop
the traffic it was generating, and one runaway integration should not consume a whole tenant's
allowance. Costs nothing — `identifyRequest` already knew the key id and was throwing it away.

## Against the graph prediction, tenth time

Shared runtime state touching auth, billing, the API and a new package. What it needed was
knowing that read-then-write races, that fixed windows leak at the boundary, and that an
office shares an IP. None of them structural.
