# T-21 — team billing and subscription limits

Plans with enforced limits, entitlements reconciled from provider webhooks, and a billing
screen. 19 new unit tests in billing plus 4 in lists, 6 new browser tests; gate 78s.

**No payment provider is wired, deliberately.** Doing so needs an account, live API keys and
a webhook secret belonging to whoever deploys this — they are not the template's to hold.
Everything around the provider is built and exercised; `docs/billing.md` names the four
functions that wire a real one, and a stub provider implements the interface so the whole
flow runs in tests.

## The prediction was right twice over

**Watch for** expected out-of-order, more-than-once webhooks and enforcement that cannot be
bypassed by calling a different endpoint. Both landed.

Two hazards, two mechanisms, and conflating them is how one silently stops working:

| Hazard | Prevented by |
|---|---|
| the same event delivered twice | primary key on `billing_event.id` |
| events arriving out of order | comparing against `subscription.last_event_at` |

The first *has* to be a constraint. Providers retry aggressively and two retries can be in
flight at once, so a read-then-write races — the same argument as [[L-035]], arrived at
independently. The second cannot be a constraint: an older event is a legitimate delivery
that must be recorded and **not applied**, which is why `billing_event` carries a
`skipped_reason` rather than being deleted.

A duplicate answers `200`. Anything else makes the provider retry harder and eventually
disable the endpoint.

## Enforcement, and the endpoint that proves it

The limit is checked inside `createList`, not in the action. Every entry point reaches that
function, so there is no endpoint to call instead — and the browser test proves it by
creating three lists in the UI, then trying a fourth **through the public API with an API
key**. Same query, same refusal.

That test also found the API returning `500` for a plan limit. A 500 tells an integrator to
retry, and retrying is exactly what will never help. It is now `402 limit_exceeded` with the
numbers in the message.

## A cycle that was a design error

Billing counted `list` rows to know usage. It typechecked, and no boundary rule objected —
every table lives in `packages/db`, so "never read another feature's tables" was satisfied
by construction. Then the test imported `createList` and Turbo refused the graph:
`@keel/billing` and `@keel/testbed-lists` each depended on the other.

The devDependency made a latent problem structural. A platform capability was counting rows
owned by a testbed feature, which would have meant every new limited resource being added to
*billing* rather than to the feature that has it.

`checkLimit(organizationId, limit, used, db)` now takes the count from its caller. Billing
owns plans, entitlements and reconciliation; features own their rows. **A cycle is rarely a
packaging accident — it is two modules that each believe they own the same fact.** [[L-044]].

Worth noting what did not catch it: the rule about reading another feature's tables protects
against taking their *data*, and has nothing to say about taking their *responsibility*.

## Decisions that are product decisions

- **`past_due` keeps its entitlements.** Cutting a customer off the moment a card expires
  loses their access over something they can usually fix in a minute, while the provider is
  still retrying the charge.
- **`canceled` drops to free, not to nothing.** A former customer can still read and export
  what they wrote. Deleting access is not the same as ending a subscription.
- **`null` means unlimited, not a large number.** `Infinity` does not survive JSON, and a
  sentinel like `999999` eventually renders as "999,999 lists remaining" — which is how you
  find out it was a sentinel.
- **Seats are stored, not derived.** A tenant that downgrades keeps its members; the limit
  governs growth rather than existing state, so nobody is locked out by a billing change.
  Enforcement on invite is recorded as T-24 rather than done here, because refusing an
  invitation needs a message in a place that does not exist yet.

## Against the graph prediction, ninth time

The dependency cycle is the closest anything has come to needing structural analysis — and
Turbo already does it, on every build, for free. That is the shape the graph prediction keeps
losing to: the checks that matter are the ones already running.
