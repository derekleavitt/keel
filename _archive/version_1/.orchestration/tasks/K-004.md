# A feature branch's new tables never reach the dev database, so the app cannot be run

## Friction

`.claude/rules/database.md` forbids generating a migration on a feature branch, so a
branch that adds `packages/db/src/schema/<feature>.ts` has tables that no migration
creates. [[L-017]] closed half of that: `createTestDatabase()` now derives the pending
delta, so unit tests see the new tables.

The other half is still open. `pnpm db:migrate` applies committed migrations only, so the
**real** Postgres a developer or the browser suite talks to does not have the tables. On
T-05 the whole unit suite was green while `/lists/[id]` would have 500'd against the dev
database, and `KEEL_E2E=1 pnpm verify` could not run at all until the derived DDL was
applied to the container by hand.

That is the worst shape a gap can have: the default gate is green, and the thing it does
not cover is "does the application actually work". It also punishes exactly the agent who
follows the rule — committing a migration, which the rule forbids, is what makes the app
run.

`drizzle-kit push` is close to what is wanted but is not wired up, is interactive under
`strict: true`, and nothing tells an agent it is the sanctioned move.

## Acceptance

- [x] One documented command brings a dev database up to the working tree's schema without
      writing anything under `drizzle/`
- [x] `KEEL_E2E=1 pnpm verify` passes on a branch that adds a table, from a clean database,
      with no manual SQL
- [x] The command is named in `.claude/rules/database.md` next to the prohibition it
      relieves, so the next agent does not hand-apply DDL or commit a migration instead
- [x] Safe by construction on a dev database and impossible to point at production
