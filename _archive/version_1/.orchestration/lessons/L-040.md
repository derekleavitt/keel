# `server.close()` waits for open connections, so a test server can hang the whole run

The webhook browser tests start a real HTTP server as the receiver. Their teardown was the
obvious thing:

```ts
close: () => new Promise<void>((resolve) => server.close(() => resolve()))
```

`close()` stops the server accepting *new* connections and then waits for every existing one
to end. One of those tests deliberately holds a request open — it is the test that proves a
hanging receiver cannot slow down the app — so the callback never fired, the test process
never went idle, and a five-test file that runs in 35 seconds instead ran until the outer
timeout killed it at ten minutes.

Nothing failed. There was no error, no warning, and no indication which of the five tests was
responsible. It read as "the suite is slow now", which sent me looking at database size,
worker counts, and the feature I had just written — none of which were involved.

```ts
server.closeAllConnections();   // the line that matters
server.close(() => resolve());
```

**Any test that opens a socket, a watcher, a subscription or a child process owns closing it
forcibly, not politely.** The polite version works right up until a test deliberately leaves
something open, which is exactly what the interesting tests do.

The diagnostic worth keeping: **a suite that got slow without getting louder is usually a
leak, not a regression.** Measure a single test in isolation before believing the code under
test got slower — here one file took fifteen minutes and every individual test in it took
seconds.
