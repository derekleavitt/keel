# A per-process rate limit is the limit divided by a number nobody chose

T-22 predicted "the first piece of genuinely shared runtime state. Nothing in Keel addresses
it." That is the whole difficulty, and it rules out the obvious implementation before it is
written.

An in-memory counter is not a rate limit. It is the limit divided by however many instances
happen to be running — a number that changes when the platform scales, that nobody picked, and
that no test on one machine will ever reveal. Under serverless it is worse: every cold start
begins at zero, so an attacker who provokes new instances has no limit at all.

So the counter lives in Postgres, and the entire operation — read, roll the window, increment
— is **one** `insert … on conflict do update`. Any version that reads and then writes is two
concurrent requests away from being wrong, and concurrent requests are the entire situation a
rate limiter exists for. The test that matters fires twenty simultaneous attempts at a limit
of five and asserts exactly five were allowed.

Third time this pattern has decided a design: idempotent recurrence ([[L-035]]), billing event
replay (T-21), and now this. **When correctness depends on "nobody else did this at the same
moment", it belongs in a constraint or a single statement, never in a check.**

## Two more decisions worth keeping

**Sliding window, not fixed.** A fixed window lets a client spend its whole allowance at 0:59
and again at 1:00 — twice the limit in two seconds, with every individual window compliant.
Keeping the previous window's count and weighting it by the remaining overlap removes that for
one extra integer.

**Limit before authenticating.** A limit that only counts successful requests leaves someone
working through stolen keys entirely unmetered, because every attempt fails auth. The address
check runs first for exactly that traffic.

## The limit that was too tight, found by the suite tripping it

The address limit started at 120/minute and the browser suite exhausted it against itself —
every test runs from one address. That is not a test artefact; it is the same arithmetic an
office behind one NAT does, and it would have shipped as "the API randomly returns 429 for our
whole company".

**An address is a blunt identifier and its limit should be generous.** The per-credential limit
is where the accounting belongs. Related: [[L-039]], where the auth rate limiter had the same
shape of problem and had never been exercised at all.
