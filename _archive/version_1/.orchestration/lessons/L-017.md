# An all-optional object type accepts any object, so it cannot guard a parameter slot

Adding a `filter` parameter to `listTodos` before the trailing `database` parameter broke
every existing caller — and **TypeScript did not catch it**.

`TodoFilter` is `{ done?, priority?, dueOnOrBefore? }`. Every field is optional, so *any*
object satisfies it. Excess-property checking only applies to object literals, not to
variables, so `listTodos(userId, listId, database)` typechecked cleanly with the database
handle sitting in the filter slot. The real database then defaulted to `db()`, and the
failure surfaced as `DATABASE_URL: expected string, received undefined` — an error that
says nothing about the actual mistake.

Two things follow, and the second matters more:

1. **An all-optional type provides no positional protection.** Never rely on one to
   distinguish arguments.
2. **Do not insert positional parameters before the database handle.** Every query helper
   in this repo ends with `database: XDatabase = db()`, and that position is load-bearing:
   callers, tests and the reference example all assume it. New options belong *inside* the
   existing filter object, not in a new slot.

Enforced through `examples/notes`, which documents the parameter order as a contract
rather than a style preference. The tests caught this one; the next occurrence might be a
query that silently runs unfiltered.
