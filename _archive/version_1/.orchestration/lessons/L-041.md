# Two parallel runners that each size themselves to the machine will multiply, not share

The unit step went from seconds to **over fifteen minutes** and started failing packages at
random. Every individual suite still finished in seconds when run on its own.

Turbo runs each package's tests concurrently. Vitest, inside each of those, sizes its worker
pool to the machine. Neither knows about the other, so twenty-odd packages each claimed ten
cores: load average past sixty on a ten-core laptop, and `@keel/testbed-todos` — 74 tests,
25 seconds alone — taking over ten minutes.

Every PGlite suite boots its own WebAssembly Postgres, so each fork is expensive in memory
as well as CPU. The suites were not slow; they were queueing.

**Cap the inner one and let the outer one schedule.** `maxForks: 2` per package plus
`turbo --concurrency=4` keeps the step inside the machine. The parallelism that pays is
across packages, which Turbo already provides; inside a package the work is mostly waiting
on WASM Postgres.

## Why this was expensive to diagnose

The failures were **timeouts in whichever package lost the race**, so the symptom pointed at
`@keel/db` — which passed 16/16 on its own, twice. I checked table sizes, connection counts,
stale locks, the schema I had just changed, and the Postgres container, all of which were
healthy, before looking at how many processes were running.

Two habits would have saved most of it:

- **When a suite gets slower without getting louder, count the processes before reading the
  code.** `uptime` and `ps aux | grep -c node` were the two commands that mattered, and I
  ran them last.
- **Measure one unit in isolation first.** A file taking 12 seconds alone and 10 minutes in
  its package is a scheduling fact, not a code fact, and the ratio says so immediately.

I also made this considerably worse for myself: repeatedly interrupting runs left orphaned
workers holding cores, so several "measurements" were taken on a machine still busy with the
previous experiment. **A benchmark on a polluted machine is not a slow result, it is no
result** — kill the strays and wait for the load average to fall before believing a number.

Related: [[L-016]], where the same suite was fixed by snapshotting the migrated database
instead of re-migrating per test. Same lesson from the other side: test infrastructure has a
performance budget, and exceeding it produces failures that look like product bugs.
