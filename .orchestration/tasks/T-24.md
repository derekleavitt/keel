# Enforce the seat limit when inviting

`subscription.seats` is reconciled from the provider, counted against membership, and shown
on `/settings/billing`. It is not enforced: an organisation on a 1-seat free plan can invite
as many people as it likes.

Lists are enforced in the query layer, which is the pattern to copy — `inviteMember` is the
equivalent seam, and covering it there means the API cannot bypass it either.

## Acceptance

- [x] An invitation beyond the seat allowance is refused with the numbers in the message
- [x] Enforced in the query layer, so the public API is covered by the same check
- [x] Downgrading below current usage does not remove anybody — it blocks *adding*
- [x] A test proves the limit is per organisation

## Watch for

The downgrade case is the interesting one. A tenant that drops from 10 seats to 1 still has
10 members, and locking nine of them out to enforce a limit is a worse outcome than letting
the count sit over. The limit governs growth, not existing state.

## Outcome

The mechanism was ten lines and correct immediately; the **number** was the design. A one-seat
free plan made collaboration a paid feature and broke every sharing test — free now allows
three. See [[L-046]].

Also revealed that `packages/organizations` had no unit tests at all, despite owning `Scope` since T-11.
It has eight now.
