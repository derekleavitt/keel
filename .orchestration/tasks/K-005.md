# Overlapping mutations need a queue, not a per-feature workaround

## Friction

Two server-action mutations fired in quick succession can silently drop one: the second
row re-renders from server state fetched before the first write landed. See
`.orchestration/lessons/L-021.md`. Removing the redundant `router.refresh()` does not fix
it.

Every feature that mutates from a list — todos, tags, and every one after them — has the
same exposure, and each will otherwise invent its own guard or, more likely, not notice.

## Acceptance

- [ ] A shared client helper in `@keel/ui` serialises mutations so a refresh cannot render
      state predating an in-flight write
- [ ] Optimistic state survives until its own write settles, not until any refresh arrives
- [ ] A browser test fires two overlapping mutations with no settle-wait and both persist
- [ ] `examples/notes` or `.claude/rules/web.md` shows the pattern, since the naive version
      looks correct and passes every single-row test
- [ ] The workaround waits in `filters.spec.ts` are removed once it holds
