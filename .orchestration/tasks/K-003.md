# No owning package for framework APIs a feature package legitimately needs

## Friction

`testbed/lists` server actions must invalidate the Next cache after a mutation, which
means `revalidatePath` from `next/cache`. CLAUDE.md forbids a feature package taking a
`next` dependency, and `packages/auth/src/next.ts` is offered as the pattern — but auth
solves this only for `headers()`, by exposing `requireUser()` instead. Nothing owns
`revalidatePath`.

Predicted during run 2 as `.orchestration/lessons/L-008.md` and never demanded until now.
Three agents in that run each worked around it differently: one returned a hint for the
app layer to act on, one added `next` as a peer dependency, one shipped without
revalidation and let the page go stale.

The architecture already states the principle — *"a feature package needing a framework
API is the same smell; the owning package should expose it"* — but named no owner. So one
must exist.

## Acceptance

- [x] `@keel/runtime` owns the framework APIs feature packages may use
- [x] `testbed/lists` invalidates the cache without depending on `next`
- [x] The re-exports are documented with *why* each is allowed through the boundary
- [x] CLAUDE.md names it, so the next agent does not re-derive a workaround
- [x] L-008 promoted from `rule` to a stronger enforcement
