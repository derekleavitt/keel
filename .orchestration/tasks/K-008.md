# A deployment story that has actually been run

The last open row in `docs/platform-readiness.md`. Everything else on that list is built and
exercised; this one has never been tried at all — there is no Dockerfile, no production
compose file, and no document saying how a reader would put this anywhere.

Pulled by need rather than predicted: with the testbed backlog empty, the only thing standing
between this template and someone using it is that nobody has ever deployed it.

## Acceptance

- [x] A production image builds from a clean checkout
- [x] That image boots and serves against a real database, verified rather than assumed
- [x] Migrations have a documented place in the deploy sequence
- [x] The worker endpoint has a documented schedule
- [x] Vercel and container paths both written down, with the differences named

## Watch for

The honest limit: deploying to a hosting provider needs an account and credentials belonging
to whoever owns the deployment. What can be verified here is the container — built, booted and
serving. Anything claimed beyond that is untested, and should say so rather than being
presented as done.

## Outcome

The container is genuinely exercised — built, booted, migrated, served, written to, and
verified refusing an unauthenticated worker call. Hosting is documented and **untested**, and
the readiness row says so rather than claiming otherwise.

Tearing the new stack down deleted the development database: two compose files in one
directory share a project, so `down -v` removes both. See [[L-047]].
