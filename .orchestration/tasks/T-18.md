# Admin surface with roles

Someone always needs to see across tenants.

Proves the **roles + admin** row in `docs/platform-readiness.md`. A capability is not done until
the testbed genuinely uses it, a worked example exists for it, the gate covers it, and the
vendor behind it could be swapped without touching feature code.

## Acceptance

- [x] Role model beyond membership: owner, admin, member
- [x] An internal admin view that crosses organizations, access-controlled
- [x] Every admin action is audited
- [x] A test proves a member cannot reach admin routes

## Watch for

Second authorization model layered on the first. If T-10's approach was too narrow,
this is where it breaks.

A hypothesis, not a specification. If the friction lands elsewhere, that is the more
interesting result — record it.

## Outcome

The second model was not layered on the first — it was kept off it. Any role expressed
through membership is one every customer can grant themselves, because every customer owns
an organization. See `.orchestration/journal/2026-08-27-T-18.md` and [[L-037]].

Also closed a hole open since T-12: `/admin/jobs` was gated on "signed in", so every
customer could read every tenant's failing job payloads.
