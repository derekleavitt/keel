# Team billing and subscription limits

Any commercial platform needs it, and it is the hardest thing to bolt on late.

Proves the **payments** row in `docs/platform-readiness.md`. A capability is not done until
the testbed genuinely uses it, a worked example exists for it, the gate covers it, and the
vendor behind it could be swapped without touching feature code.

## Acceptance

- [x] Plans with enforced limits — seats, lists, storage
- [x] Provider webhooks reconcile subscription state idempotently
- [x] Limits enforced server-side at the query layer
- [x] Deployment documented and actually exercised

## Watch for

Provider webhooks arrive out of order and more than once. Idempotency again, and
enforcement that cannot be bypassed by calling a different endpoint.

A hypothesis, not a specification. If the friction lands elsewhere, that is the more
interesting result — record it.

## Outcome

Both predicted hazards landed and needed two separate mechanisms: a primary key for
duplicates, a timestamp comparison for ordering. Enforcement sits in the query layer and is
proven unbypassable by a browser test that tries the public API instead.

No payment provider is wired — that needs credentials belonging to the operator. See
`docs/billing.md`, and [[L-044]] for the dependency cycle this exposed. Seat enforcement on
invite is T-24.
