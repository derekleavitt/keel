# Make lockfile release ownership-checked and staleness configurable

`lockfile.mjs`'s own header admits "a slow holder can have its lock taken while it still believes it owns it" but nothing tests it, and the code makes it worse than described: the lock's content is only a timestamp, so when the slow holder resumes it (a) writes its stale read-modify-write over whatever the new holder wrote, and (b) `finally { fs.unlinkSync(lockPath) }` deletes the *new* holder's lock, letting a third worker in. The header's "30/30 after the fix, 10/10 at twenty agents" claim is not asserted anywhere. `STALE_MS` and `RETRY_MS` are hardcoded, which makes the reclaim path a 10-second test.

## Acceptance
- [ ] Lock content is `<pid>:<random token>:<timestamp>`; a holder re-reads the lock immediately before writing the data file and before unlinking, and aborts (throws a distinct `LockLostError`) if the token is not its own, so it never overwrites or unlinks another holder's work
- [ ] `STALE_MS` and `RETRY_MS` read `SORTLAB_STALE_MS` / `SORTLAB_RETRY_MS` from the environment with the current defaults
- [ ] `SORTLAB_STALE_MS=500 node src/run.mjs --agents 8 --strategy lockfile --slow 1 --slow-ms 1500 --trials 5` exits 0 (before this task it loses updates; a test asserts the post-fix pass)
- [ ] `node src/run.mjs --agents 20 --strategy lockfile --trials 10` exits 0 (pins the "10/10 at twenty agents" claim)
- [ ] `test/lockfile.test.mjs` includes a unit test that writes an unparseable lock file and asserts `acquire` does not take it within 200ms (fail-closed), and one that writes a lock with a timestamp older than `SORTLAB_STALE_MS` and asserts `acquire` takes it
- [ ] `node --test test/lockfile.test.mjs` exits 0 in under 30s

## Notes
- Depends on T-007 for `--slow/--slow-ms`. If running before T-007 lands, the equivalent is a worker with `--delay` larger than `STALE_MS`, but do not edit `run.mjs` here.
- Export `acquire`/`release` (currently module-private) so the unit tests can call them directly.
- The stale-reclaim path (`unlinkSync(lockPath)` after reading an old timestamp) still has a TOCTOU: two workers can both read "stale", one reclaims, the other deletes the fresh lock. A cheap mitigation is to re-read and compare content immediately before the unlink; note in the header that POSIX offers no compare-and-unlink and this remains best-effort.
- `LockLostError` should make the worker exit non-zero; the harness will then report the trial honestly instead of passing with a lost update.
