# Recurring todos

Reminders, digests, cleanup and billing runs all need scheduled work.

Proves the **scheduling** row in `docs/platform-readiness.md`. A capability is not done until
the testbed genuinely uses it, a worked example exists for it, the gate covers it, and the
vendor behind it could be swapped without touching feature code.

## Acceptance

- [x] A recurrence rule persists and generates future instances
- [x] Generation is idempotent — running twice does not duplicate
- [x] Timezone-correct, tested across DST boundaries
- [x] Editing a series versus a single instance is unambiguous

## Watch for

Idempotency is the hard part and Keel says nothing about it. Expect a lesson.

A hypothesis, not a specification. If the friction lands elsewhere, that is the more
interesting result — record it.

## Outcome

Idempotency was not hard once it moved into a partial unique index with
`on conflict do nothing` — the difficulty was date arithmetic, not concurrency. See
`.orchestration/journal/2026-08-27-T-17.md`, [[L-035]] and [[L-036]].

The **Watch for** was right that Keel said nothing about idempotency and right to expect a
lesson. It produced two: uniqueness stops duplicates, a watermark stops resurrection, and
neither substitutes for the other.
