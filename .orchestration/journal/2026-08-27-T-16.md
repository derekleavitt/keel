# T-16 — outbound webhooks

Signed, retried, replayable delivery of todo events to subscribed receivers, with an SSRF
guard on the URL. 54 new unit tests, 5 new browser tests; 65 browser tests green.

## The task's hypothesis, and what it actually found

**Watch for** asked whether the queue from T-12 was "genuinely reusable rather than shaped
only for email". It was — `enqueue`, backoff, dead-lettering and the handler registry all
took a second consumer with no changes at all.

It also **had never run**.

The first time anything drained that queue over HTTP against the real development
database, its claim query threw. Twice, for two unrelated reasons, in the same ten lines:
`postgres` refuses a `Date` as a parameter where PGlite accepts one, and `postgres` returns
rows as an array where PGlite returns `{ rows }`. Drizzle's query builder hides both; a raw
`` sql`…` `` template hands values straight to the driver and returns what it returns.

Thirteen unit tests, a dead-letter path, an admin page, a green gate — and the central
query of the capability had never once executed against the driver it ships with. The unit
suite could not have caught it, and its passing was not evidence of anything. [[L-033]].

I have updated `docs/platform-readiness.md` to say what "done" has to mean, and marked the
queue done *at T-16* rather than T-12. The reusability question was answered; the more
useful answer was to a question nobody asked.

## Two stages, and why

A mutation calls `emit()`, which writes exactly one job row in the mutation's own
transaction. No endpoint lookup, no network, no fan-out. The worker then expands that into
one delivery per subscriber, each with its own job and its own retry budget.

This is what makes "a slow receiver cannot slow down the app" true rather than aspirational:
at write time nobody has been contacted, so there is nobody to wait for. There is a browser
test with a receiver that accepts the connection and never answers, asserting the mutation
still completes in under five seconds against a ten-second delivery timeout.

Fanning out inside one job would put every receiver behind the slowest, and a retry would
re-POST to the ones that already succeeded. Same reasoning as T-12's digest.

The two stages are always one worker pass apart, because `runJobs` fixes its "now" at the
start of a pass and the delivery job is enqueued during it. Obvious in hindsight; it cost a
confusing test failure first.

## Signing, and shipping the verifier

`keel-signature: t=<unix>,v1=<hmac-sha256 of "t.body">`. The timestamp is *inside* the
signed string, which is what stops a captured delivery being replayable forever — signing
the body alone makes every delivery valid for all time. A stale or future `t` is rejected
even when the digest matches, and there is a test that re-stamps a valid digest to prove it.

`verifySignature` is exported rather than described, because a signing scheme with no
shipped verifier is one every integrator implements slightly differently, and the
differences are all security bugs.

The unit tests stub `fetch`, which proves the logic and cannot prove a receiver on the far
side of a socket can verify what actually arrives. The browser test starts a real HTTP
server and verifies with the shipped verifier over the bytes that crossed the wire. That
distinction is the whole lesson above, applied.

## The guard that made the feature untestable

A webhook URL is attacker-supplied input the *server* fetches — SSRF by construction.
Unguarded, any tenant can point one at `http://169.254.169.254/` and read the instance's
own cloud credentials.

The guard was easy. The problem it created was not: a developer's receiver is on
`127.0.0.1`, which is exactly what the guard blocks. Left there, nobody would test webhook
code until production — and the predictable end is somebody permitting loopback
unconditionally "for dev" and shipping the hole everywhere.

So: `WEBHOOK_ALLOW_PRIVATE_HOSTS`, off by default, **refused by the environment contract
when `NODE_ENV=production`** so the app will not start rather than run unguarded, never
unblocking cloud metadata, and written into a fresh `.env` by `pnpm db:up` so the working
local default is the safe one. Refusing to start beats warning: a warning is read once and
then filtered. [[L-034]].

A smaller instance of the same principle sits next to it. Deciding the URL policy means
reading the environment, which can fail — and the fallback is the *strictest* policy, not
the most convenient. A control must never widen because configuration is missing; the
environments least likely to be configured are the ones where nobody would notice.

## L-029 caught me with my own lesson

`page.getByRole('alert')` in the new spec was a strict-mode violation on the first run:
Next renders its own `role="alert"` route announcer into every document, so that query is
ambiguous on *every page in the app*, not merely crowded ones. Added to the roles the
scoping check rejects.

## Against the graph prediction, fourth time

A cross-cutting delivery mechanism touching the queue, the schema, three feature packages
and the app is exactly what a code graph is sold for. What actually found the problems was
running the thing: two driver incompatibilities, an assertion about replay that described a
behaviour the button never promised, and a role that collides with a framework element.
None are structural facts. The graph prediction remains unearned.
