# T-15 — public API with API keys

`/api/v1` for lists and todos, authenticated by revocable per-organisation keys, documented
in `docs/api.md`. 17 new unit tests, 8 new browser tests; 60 browser tests green.

## The task's hypothesis was right, and the answer was one layer down

**Watch for** predicted: "whether `requireScope()` generalises or has to be rebuilt is
exactly the kind of thing only a second caller reveals." It does not generalise, and the
reason is the most useful thing this task produced.

`requireScope()` ends in `resolveScope()`, which falls back to the caller's personal
workspace when the requested organization is not one they belong to. That is right for a
browser — a stale cookie should not 500 a signed-in user. Reused for a key it is a tenancy
breach: a key issued for Acme, presented after its owner leaves Acme, would resolve to that
person's private workspace and answer `200`. An integration pointed at one tenant, quietly
operating on another, with nothing in the logs looking wrong.

Neither "reuse it" nor "rebuild it" was the answer. The shared primitive is `scopeFor()`,
the strict membership check both mechanisms already sat on top of. Session auth wraps it in
a fallback because a human can be redirected; key auth calls it directly because a script
cannot. One authorization path, as the acceptance criterion asked, but not the one I would
have picked before looking. [[L-031]].

That check runs on **every** request rather than being trusted from the key's row, which is
what makes removing someone from an organisation revoke their keys for it immediately, with
nothing to invalidate.

## Split tokens

`keel_sk_<16 hex selector><48 hex verifier>`. The selector is stored in the clear and
uniquely indexed; only the verifier is hashed. Storing half the token in the clear looks
wrong and is not: it identifies the row and grants nothing, and it turns verification into
one indexed lookup. Hashing the whole token forces either a scan that hashes every
candidate, or an unsalted hash used as a lookup key — the same exposure, slower.

SHA-256 rather than bcrypt, deliberately. A key is 128 bits of machine randomness; there is
no dictionary to slow down, so a password hash would add latency to every API request and
defend against nothing.

Unknown selector, wrong verifier and revoked key all return null, and the verifier
comparison is `timingSafeEqual`. Distinguishing those cases — by response or by timing —
tells an attacker which half of a guess landed.

Revocation is a timestamp, not a delete: a revoked key that vanishes takes with it the
answer to "was this key live when that happened", which is the question asked after a leak.

## 404, not 403

Another tenant's list answers `404`. A `403` confirms the id exists, which makes the API an
enumeration oracle. This needed no special case — the query layer already returns nothing
for "not yours" and "no such thing" alike, so the honest answer and the safe answer are the
same one. Both the index and the by-id route are tested, because a filtered index with an
unfiltered detail route is the classic form of this bug.

## The T-14 decision paid for itself immediately

Nothing in any route handler mentions the audit log, and API activity is recorded anyway —
because the endpoints call the same query helpers the browser does, and `audit()` sits
beside the write. There is a browser test that creates a todo over HTTP and finds it in the
feed. Had the recording gone in the server action layer, as I first wired it, this would
have been a silent gap discovered by a customer. [[L-028]].

## A type-only import the rules forbid

`parseBody(request, schema: ZodType<T>)` does not compile in `apps/web`: Zod is not a
dependency there and must not become one. Rather than adding it or casting to `unknown`,
`@keel/contracts/parse` publishes a six-line structural `Parser<T>` that every schema
satisfies. Full inference in the app, no vendor import, and swapping validators changes one
file. [[L-032]].

## Against the graph prediction, third time

A second authentication mechanism touching every entry point is the archetypal case for
"the graph will tell you what this affects". What actually told me was `tsc` refusing the
`ZodType` import, `grep` for `requireScope`, and reading `resolveScope` — twelve lines whose
*fallback branch* was the whole finding. No call graph would have flagged that branch;
it is a semantic property of what the function does when it fails, not a structural one.

Three features running, the predicted need has not appeared. P1-03 and P4-05 stay for now,
but this is the strongest evidence yet that the type system plus a fast gate is doing the
job the graph was designed for.
