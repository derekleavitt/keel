# K-008 — a deployment story that has actually been run

The last open row in `docs/platform-readiness.md`. Every other capability had been built and
exercised; this one had never been attempted — no Dockerfile, no production compose file, and
nothing telling a reader how to put this anywhere.

## What was verified, and what was not

**Verified, on a laptop:** the image builds from a clean checkout, boots against a real
Postgres, applies 21 migrations to an empty database, serves pages, signs a user up, writes
the row, serves its static assets, and refuses an unauthenticated worker call while processing
a job when authorised.

**Not verified:** deploying to any hosting provider. That needs an account and credentials
belonging to whoever owns the deployment. `docs/deployment.md` says so at the top and presents
the Vercel section as a checklist rather than a guarantee — the readiness row reads
"done (container exercised)" for the same reason. Marking it plainly done would have been the
easy lie.

## Three decisions in the Dockerfile

**Two stages, not the usual three.** A separate `deps` stage that installs and hands
`node_modules` to the build is the standard pattern and does not work with pnpm: the install
is a symlink farm, and `COPY --from` flattens the links into directories, so the build stage
reinstalls anyway. The store cache mount gives the same caching without the pretence.

**The runtime carries no toolchain.** No package manager, no compiler, no source — only Next's
traced `standalone` output, as a non-root user. Size is the lesser benefit; the real one is
that nothing in the image can install or build anything.

**The build runs with no environment at all.** That is not incidental — it is where the lazy
`serverEnv()`, `db()` and `auth()` guarantee is tested. If this step ever starts demanding a
`DATABASE_URL`, something has been hoisted to module scope, and the Dockerfile says so.

## Migrations are a release step

`docker-compose.prod.yml` runs them as a separate service, from the build stage, with the app
waiting on `service_completed_successfully`.

Not on boot. Every replica would run the migration, concurrently, at exactly the moment a
rolling deploy starts several of them — a race whose failure mode is a half-applied schema.
The document also states the constraint that follows from a deploy never being atomic: for
some window both versions run against one schema, so a rename or drop takes two deploys.

Running them from the *build* stage is the honest consequence of the runtime having no
toolchain. The alternative — adding `drizzle-kit` to the runtime image — would trade away most
of what makes that image small in order to make one release step marginally more convenient.

## I deleted the development database

Tearing the new stack down did it:

```bash
docker compose -f docker-compose.prod.yml down -v
```

Compose derives its project name from the **directory**, not the file, so both compose files
belonged to one project — and `-v` removes the *project's* volumes, not the file's. `keel-pgdata`
went with it. Nothing warned; the command reported success.

`pnpm db:up && pnpm db:migrate` rebuilt it in thirty seconds, which is the only reason this is
a lesson rather than an incident. The same command against a directory whose compose file
named a production volume would not have been recoverable.

Two things were mine rather than Docker's. I ran a destructive flag as cleanup without asking
what it considered "state" — `docker compose config --volumes` answers that in one command and
would have cost nothing. And my first fix made it worse: naming *both* projects orphans the
container and volume of every checkout that already has a stack running, so `pnpm db:up` then
fails on a name conflict. Naming one side is sufficient. A safety fix that breaks working
machines is not an improvement. [[L-047]].

## The template could not build its own image

`apps/web/public` did not exist, so the `COPY` failed. A small thing, and worth noting as the
class of problem this task exists to find: nothing before it had ever built the image, so
nothing had ever needed that directory. It contains a `robots.txt` now.
