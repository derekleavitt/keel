# T-18 — admin surface with roles

Platform staff as a separate authorization axis, a cross-tenant admin area behind a single
gate, and every staff action recorded in two places. 36 new unit tests, 6 new browser tests;
79 browser tests green.

## The question the task asked, and the answer

**Watch for** predicted a "second authorization model layered on the first" and asked
whether T-10's approach was too narrow. It was not — but only because the second model was
kept off it entirely, and the reason is one line:

> Every customer can create an organization, and is automatically its owner.

So any role expressed through membership is a role every customer can grant themselves.
Extending `membership_role` with a `staff` value, or treating admin of a designated internal
organization as staff, both hand every customer the ability to read every other customer.
"Admin of my own workspace" and "may read every workspace" share a word and nothing else.

Separate axes, separate storage: `membership.role` for tenancy, a `platform_admin` table for
staff. Nothing a request can reach writes to that table — the only path is
`pnpm admin:grant`, which needs shell access to the deployment. [[L-037]].

## A hole that had been open since T-12

`/admin/jobs` shipped with T-12 checking only that the caller was signed in. Its own comment
said proper gating would arrive with T-18 and explained why that was acceptable in the
meantime. It was not: any customer could read every tenant's failing jobs, payloads included.

The fix is structural rather than local. The gate is `app/admin/layout.tsx`, which covers
every route beneath it, so a new admin page is protected by existing. A per-page check is one
page away from being forgotten, and the page somebody forgets is the one that crosses
tenants — silently, looking like a working feature.

It answers 404 rather than 403. A 403 confirms the area exists and the reader is merely not
allowed, which is where an attacker would then spend their time.

An honest comment describing a known gap is worth very little. This one was accurate, dated,
and sat in the tree for six tasks.

## Two logs, on purpose

Staff actions go to `admin_action`, not `audit_entry`. The tenant log is scoped by
`organization_id`, and that scoping is exactly what makes it safe to show a customer — a
platform action often has no tenant at all, and a nullable column there would weaken the one
guarantee the tenant log rests on.

When an action does name a tenant it is written to **both**, attributed to the staff member's
real email. A log only the vendor can read is not the same promise as one the customer can
read, and "someone at the vendor opened your account" is a worse answer than a name.

Reads are recorded too. Support mostly looks at things, and "who opened this account" is the
question that actually gets asked — an action log covering only writes cannot answer it.

## The CLI that could not import its own module

`platform.ts` held everything about staff, including `requirePlatformAdmin()`. It typechecked
and the app worked. Then `pnpm admin:grant` — the only way the first administrator can be
created — failed at import with `Cannot find package 'next/headers'`, because one function in
the module resolved the current session and that made the whole module request-only.

Split along "does this need to know who is asking": the request-bound half went to
`session.ts` with the other `require*` helpers, and the rest now works from a CLI, a job, a
test and a request alike. The signal is a heavy import that only one function needs. [[L-038]].

## A boundary this exposed and did not fix

`packages/testbed-admin` composes across organizations, jobs, webhooks and audit, and lives
in `testbed/` because organizations do — `@keel/organizations` owns the queries even though
`Scope` is now a Keel primitive that every package depends on.

That is backwards, and it is the kind of thing this project is meant to surface: multi-tenancy
graduated from testbed experiment to platform foundation somewhere around T-11, and the
package layout never caught up. Not fixed here — it is a rename touching every import in the
repo and does not belong bundled with an admin surface. Recorded as its own task instead.

## A bug only the full suite could find

The staff user search passed alone and failed in the full run. `findUsers` had a `LIMIT`
with no `ORDER BY`, so which rows came back was arbitrary — fine with a handful of accounts,
and wrong once the suite had created enough to exceed the limit. The account being searched
for simply was not in the results, with nothing to indicate the list had been truncated.

Worth noting how it was nearly misdiagnosed: it looked exactly like flakiness, and passed 18
consecutive times in isolation. The tell was that the failure text contained twenty-five
results — a round number, and the limit.

`ORDER BY` now pairs with the limit, and a unit test asserts two identical searches return
identical pages. A support tool that silently omits the account you are looking for is worse
than a slow one.

## Against the graph prediction, sixth time

A second authorization model spanning auth, orgs, the app and four existing pages is exactly
the case for "the graph will tell you what this affects". What actually mattered was noticing
that every customer owns an organization — a semantic fact about sign-up, not a structural
one — and a CLI failing at import. Neither is in a call graph.
