# T-20 — real-time list updates

A change made in one tab appears in another without a refresh, over server-sent events
backed by a Postgres change log. 14 new unit tests, 6 new browser tests; 88 browser tests
green, gate 83s.

## The prediction was right, and the reason is time

**Watch for** expected the server-action model to "have nothing to say about" a stateful
connection. It doesn't, and the gap is sharper than a missing helper.

Every authorization here resolves at the moment of a request and is then discarded. A server
action that took a second longer would still be correct, because it re-asks on the next call.
**A stream has no next call.** Authorizing at connection time and holding the socket open
turns the decision into "whatever was true when they connected" — revoke a share, and that
tab keeps receiving change notifications until it is closed. Not the contents, but the
timing, which is enough to know who is working on what and when.

So the stream re-authorizes on a timer and closes itself with a `revoked` event. The question
a long-lived connection asks is not "may they" but "may they *still*". [[L-042]].

## A table, not LISTEN/NOTIFY

`NOTIFY` delivers to whoever is connected at that instant and to nobody else, so "reconnects
recover missed state" cannot be built on it without adding a durable log anyway — and it
needs a held-open connection per listener, which is what serverless deployment does not give
you.

A `change_log` table with a monotonic id makes the cursor trivial, and makes **reconnection
and first connection the same code path**. That matters more than the mechanism: the recovery
path runs on every page load rather than only during the incident it exists for.

The cost is polling the log instead of being pushed to. It is real, bounded, and written down
beside the table.

## The stream carries no data

A notification is `{"channel":"list:abc"}`. The client refetches through the ordinary
authorized query.

Not a bandwidth decision. Pushing rows would mean re-implementing every visibility rule at
the socket layer, where getting it wrong fails open — a subscriber seeing data no page would
have shown them. Sending only "something moved" makes the worst case a refetch that returns
nothing.

## SSE over WebSockets

The traffic is one-directional, and so is SSE. It is also plain HTTP: it survives proxies and
CDNs that block socket upgrades, and the browser reconnects on its own, resending
`Last-Event-ID` — so the cursor survives a dropped connection with no client bookkeeping at
all. A WebSocket would buy bidirectionality nothing here needs and cost every one of those.

The degraded path is the **same endpoint** with `?poll=1`: same authorization, same cursor,
same tests. A fallback that shares nothing with the primary path is a fallback nobody
notices has rotted.

## The bug the fallback found

`cursor === 0` meant "not supplied", so a fresh subscriber started from now instead of
replaying history. `0` is also the real cursor of **every tenant that has never changed
anything** — so the first change in a new workspace was fast-forwarded past and never
delivered. Nothing errored; the subscription connected, reported itself live, and stayed
silent.

Both streaming tests passed throughout, because a live subscriber's first change arrives when
its cursor is already non-zero. The test that caught it was the polling one, driving the
endpoint with explicit cursors. A degraded path tested as rigorously as the primary one is a
second pair of eyes on the same logic, and here it was the pair that could see. [[L-043]].

## A third shape of `requireScope`

Neither existing form fits a streaming endpoint: `requireScope()` throws, which becomes a 500
rather than a 401, and `requireScopeOrRedirect()` issues a redirect an `EventSource` follows
silently to an HTML page and then fails to parse. Added `requireScopeOrNull()` — the shape an
API needs, as opposed to a page.

That is the third time this session a caller wanted the same authorization with different
failure semantics ([[L-031]], [[L-038]]). The pattern is stable enough to note: the decision
is shared, the *response to a refusal* belongs to the caller.

## Against the graph prediction, eighth time

The first stateful connection touching auth, orgs, todos, the app and a new package. What it
needed was knowing that `NOTIFY` has no replay, that `0` is a real cursor, and that
`EventSource` follows redirects. None of those are in a call graph.
