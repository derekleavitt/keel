# T-14 — activity feed

Every mutation to a list or todo now leaves a record of who did it, what happened and when,
readable per organisation at `/activity` and per list on the list's own page. 9 new unit
tests, 5 new browser tests; 52 browser tests green.

## The seam is the query layer, and finding that out cost the first attempt

The task predicted this would be "a textbook case for something the query layer provides
once". It was, but not by the route I took. I built `withAudit(operation, describe)` first —
wrap a mutation, and the entry cannot be forgotten. It typechecked, it read well, and no
call site could use it.

It could not see what happened: from outside, all a wrapper has is the return value, and
only the mutating code knows a list was renamed *from* one name *to* another. And it could
not thread the connection: every query helper takes `database` as a trailing parameter so
tests inject PGlite and deletes pass a `tx`, but a wrapper forwarding `...args` opaquely
cannot know which one that is. It would have logged through the default `db()` while the
write went elsewhere.

Deleting it and moving the call *down* — inside the query helper, beside the write, where
the row and the handle are both in scope — fixed both problems at once.

The relocation then paid for itself for an unrelated reason. **Server actions are not the
only entry point.** T-15 adds a public API and T-16 adds webhooks, both reaching these same
helpers directly. Auditing in the action layer would have recorded what the browser did and
silently missed everything else — working software right up until someone asked why API
activity was invisible. [[L-028]].

## Two columns that look wrong on purpose

`target_id` has **no foreign key**. "Who deleted this list" is asked precisely once the list
is gone, so a cascade would delete the answer along with the question. The cost is a
dangling id, which is correct: the row records an event, not a relationship. There is a
browser test that deletes a list and then finds both its creation and its deletion still in
the feed.

`actor_email` is **denormalised**, copied at write time rather than joined on demand. An
account can be deleted or an address changed, and the log must still say who acted *then*.
A join would quietly rewrite history every time somebody updated their profile.

Same reasoning for `summary`: the sentence is composed when the event happens and stored
with it, so the feed renders entirely from the entry. A feed that resolves ids at read time
shows "(deleted)" exactly where the history is most interesting.

## Adding one element broke nine tests in five unrelated files

Rendering the History feed on `/lists/[id]` put a second `<ol>` on the page, and every spec
that said `page.getByRole('listitem')` silently started matching activity rows as well as
todos. Reordering, filtering and tagging all failed — six files from the cause.

None of those tests were wrong when written. The query was never "the todos"; it was "every
list item on the page", which *happened* to be the todos while the page held one list. The
real defect was that the todo list had no accessible name, so there was no way to ask for it
specifically.

Fixing the specs alone would have left the next feed to break them again, so this was
promoted past a test to a static check: `apps/web/e2e/scoping.test.ts` reads the specs and
fails on a bare role query for any role that repeats. It immediately found two more files
that were passing only by luck. Naming the containers fixed the tests and improved the pages
for a screen reader in the same change. [[L-029]].

## A silent absence, on a different page

`todo.completed` never appeared in the feed while `todo.created` did, from wiring that was
identical for both. The wiring was fine — the test was racing.

`useOptimistic` flips the checkbox before the action returns ([[L-015]]), so `toBeChecked()`
was satisfied early; the test then navigated to `/activity`, a server-rendered page, and the
entry arrived after the render that would ever be inspected. `audit()` deliberately never
throws, so nothing errored anywhere. Waiting for the control to be re-enabled — a signal the
server controls — is the fix. [[L-030]].

That "never throws" is still right: losing a user's work to preserve a line in a feed is the
wrong trade. But it means a broken audit path is invisible from the outside, which is why
the swallow is itself tested, asserting the failure reaches stderr.

## Against the graph prediction, again

Like T-11, this was supposed to be a case where a code graph earns its place — a
cross-cutting concern touching every mutation in every feature package. It wasn't. Finding
every mutation was `grep` for `.returning()`; knowing where to put the call was a type
signature question; and the one genuinely surprising consequence — nine tests breaking in
files that never mention audit — was found by running them, and is now prevented by twenty
lines that read the spec files. Second feature in a row where the predicted need did not
appear. Still not deleting P1-03, but the evidence is accumulating.
