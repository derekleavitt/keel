# With an optimistic UI, "the change is visible" no longer means "the write landed"

The activity feed recorded `todo.created` and not `todo.completed`, from wiring that was
identical for both. The audit call was correct; the test was racing.

`useOptimistic` ([[L-015]]) flips the checkbox the instant it is clicked, so
`toBeChecked()` is satisfied *before* the server action returns. The test then navigated to
`/activity`, which is a server-rendered page: the entry arrived a moment later, and
`toContainText`'s five seconds of retries re-queried a DOM that was never going to change.
Retries hide this class of bug when the assertion is on the same page and expose it as a
flake when it is not.

`audit()` deliberately never throws, so nothing was logged and nothing failed — the
symptom was an absence, on a different page, with no error anywhere.

**Assert on a signal the server controls before leaving the page.** Every mutating control
here is `disabled={pending}` while the action is in flight, so waiting for it to be enabled
again is a direct observation that the round trip finished:

```ts
await expect(page.getByLabel('Mark X not done')).toBeChecked();  // optimistic
await expect(page.getByLabel('Mark X not done')).toBeEnabled();  // actually landed
```

Optimistic state and settled state are two different assertions and both are worth making.
Checking only the first tests the client; checking only the second misses the flicker the
optimistic path exists to prevent.
