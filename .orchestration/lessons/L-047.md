# Two compose files in one directory share a project, so `down -v` on either destroys both

Adding `docker-compose.prod.yml` beside the existing `docker-compose.yml` and tearing the
first one down deleted the development database:

```bash
docker compose -f docker-compose.prod.yml down -v   # removed keel-pgdata as well
```

Compose derives its project name from the **directory**, not the file. Both files therefore
belonged to the project `boilerplate`, and `-v` removes the project's volumes — not the
volumes declared in the file that was passed to it. Nothing warned; the command reported
success.

Only the **new** file sets `name:`, which is the whole fix — one side of the pair being
distinct is enough. Naming the development one as well was the first attempt and was worse: it
orphans the container and volume of every checkout that already has a stack running, and
`pnpm db:up` then fails on a container-name conflict. A safety fix that breaks working
machines is not an improvement.

## The part that was mine, not Docker's

`down -v` is a destructive command and I ran it as cleanup, without checking what it would
take with it. The habit that would have caught it costs one command:

```bash
docker compose -f docker-compose.prod.yml config --volumes   # what will -v remove?
```

**Before a flag that deletes state, ask what it considers "state".** The scope of `-v`,
`--prune`, `-r`, `--force` is almost never the file or directory being pointed at — it is
some enclosing thing the tool defines, and the difference only becomes visible afterwards.

The damage here was a development database that `pnpm db:up && pnpm db:migrate` rebuilds in
thirty seconds, which is the only reason this is a lesson rather than an incident. Same
command in a directory whose compose file happened to name a production volume would not have
been recoverable.
