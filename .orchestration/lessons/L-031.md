# A forgiving fallback is a feature for a browser and a hole for a machine

T-15 predicted the interesting question would be "does `requireScope()` generalise to a
second caller". It does not, and the reason is worth more than the answer.

`requireScope()` ends in `resolveScope(userId, requested)`, which **falls back to the
caller's personal workspace** when the requested organization is not one they belong to.
For a browser that is correct: a stale `keel_org` cookie should land a signed-in user
somewhere sensible rather than throwing a 500 at them.

Reused unchanged for API keys, that same fallback becomes a silent tenancy breach. A key
issued for Acme, presented after its owner is removed from Acme, would not fail. It would
resolve to that person's *private* workspace and answer `200` — an integration pointed at
one tenant quietly reading and writing another, with nothing in the logs looking wrong.

The fix was not to special-case the key path but to notice that the shared thing was one
layer down. `scopeFor()` — the strict membership check — is what both mechanisms actually
have in common. Session auth wraps it in a fallback because a human can be redirected; key
auth calls it directly because a script cannot be told to pick a different workspace.

**When a second caller arrives, look for the shared primitive rather than reusing the
first caller's convenience wrapper.** Convenience is where the policy lives, and policy
written for an interactive user is rarely right for an unattended one. The generic form:
any "if that fails, try something reasonable" is a decision about what to do when
authorization is ambiguous, and every such decision needs re-taking per credential type.

Related: [[L-028]] — the same shape one level up. The layer that owns the *request* keeps
acquiring entry points; the layer that owns the *resource* does not.
