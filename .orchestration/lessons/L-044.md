# A dependency cycle is the design telling on itself

`packages/billing` needed to know how many lists a tenant had, so `checkLimit` counted them:

```ts
const [row] = await database.select({ n: count() }).from(list)
```

It typechecked. `list` comes from `@keel/db/schema`, which everything may import, so no
boundary rule objected. The test then imported `createList` to prove enforcement worked, and
Turbo refused the graph outright:

```
@keel/billing#typecheck -> @keel/testbed-lists#typecheck
@keel/testbed-lists#typecheck -> @keel/billing#typecheck
```

The devDependency made a latent problem structural. Billing — a platform capability — was
counting rows belonging to a testbed feature, so a new limited resource would have meant
editing *billing* rather than the feature that has it.

The fix inverts it: `checkLimit(organizationId, limit, used, db)` takes the count from its
caller. Billing owns plans, entitlements and reconciliation; features own their own rows and
ask whether one more is allowed. The composition happens on the page, where the dependencies
already point.

**A cycle is rarely a packaging accident — it is two modules that each believe they own the
same fact.** Splitting the fact is almost always right, and it is worth asking which of them
should own it rather than reaching for the mechanical fix of merging them or hoisting a
shared module between them.

Note what did *not* catch this. Every table lives in `packages/db`, so "never read another
feature's tables" was satisfied by construction and said nothing. The rule protects against
one package reading another's *data*; it has nothing to say about a package taking on
another's *responsibility*. Turbo's cycle check was the only thing that noticed, and only
once a test made the dependency real.

primitive is the same misplacement, still unfixed and still quiet.
