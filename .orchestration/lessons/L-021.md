# Overlapping optimistic mutations can lose a write

Firing two server-action mutations in quick succession — set a priority, then immediately
tick a checkbox — can silently drop the second. The tick appears optimistically, the
assertion for it passes, and the row then re-renders from server state fetched before the
write landed. Nothing errors. The user sees the box un-tick itself a moment later.

Only a browser catches it, and only when mutations overlap; every test that acts on one
row at a time passes.

**What was ruled out.** Each action calls `revalidatePath`, so the client's
`router.refresh()` looked redundant and a likely culprit. Removing it changed nothing —
the whole suite still passed and the race still reproduced. The cause is in how
overlapping revalidations resolve, not in the extra client call.

**Current mitigation is a workaround, not a fix.** Tests wait for each write to settle
before starting the next. That makes the suite honest but does nothing for a real user
clicking quickly.

**The actual fix is a mutation queue** in the client layer: serialise actions per row so a
later refresh cannot render state that predates an earlier write. That belongs in a shared
component rather than in every feature, which makes it Keel work rather than testbed work —
filed as `K-005`.

Recorded rather than hidden. A known limitation with a workaround is a different thing from
a passing test that quietly proves nothing. Related: [[L-015]], which established the
optimistic pattern this exposes the limits of.
