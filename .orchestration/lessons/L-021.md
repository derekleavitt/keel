# revalidatePath('/lists') does not invalidate '/lists/[id]'

**This lesson previously claimed overlapping mutations were losing writes. That was
wrong, and the correction is the useful part.**

## What I originally concluded

Setting a priority and immediately ticking a checkbox appeared to drop the tick. I
diagnosed a race between concurrent optimistic mutations, wrote it up, and built a
mutation queue in `@keel/ui` to serialise them.

The queue did not fix it. Neither did removing the redundant `router.refresh()`. Two
plausible theories, two failures — at which point guessing a third time would have been
the wrong move.

## What was actually happening

Querying the database directly after a failing run settled it in one step:

```
 title | done | priority
-------+------+----------
 Alpha | t    | high
 Beta  | f    | medium
```

**Every write had landed. Nothing was ever lost.** Five POSTs, five 200s, correct rows.

The bug was on the read side: every action called `revalidatePath('/lists')`, but the page
the user is looking at is `/lists/[id]`. Revalidating a parent path does not invalidate a
nested dynamic segment, so the server was correct while the client kept serving a cached
payload — which is indistinguishable, from the outside, from a write that never happened.

The fix is one argument: `revalidatePath('/lists', 'layout')` invalidates the segment and
everything beneath it.

## The part worth carrying forward

**Check the source of truth before theorising about the mechanism.** The symptom pointed
at concurrency, both concurrency theories were wrong, and a single `psql` query would have
redirected the investigation at the start instead of after two failed fixes.

The tests do wait for the app to go idle before reloading or navigating — but that is
waiting for the application to finish, not hiding a defect. The writes are in the database
by that point; the test simply must not outrun the round trip it is asserting on.

## What the queue was still worth

`useSerialMutations` stayed, on its own merits rather than the one it was built for: it
keeps `useOptimistic` updates inside a transition where React 19 requires them, and it
collapses a burst of clicks into one refresh instead of one per click. It was a good
change justified by a bad diagnosis. Related: [[L-015]].
