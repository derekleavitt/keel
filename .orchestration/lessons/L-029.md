# An unscoped role query is a latent conflict that a second element resolves against you

Adding a History feed to `/lists/[id]` broke nine browser tests in five files that had
nothing to do with the audit log. None of them were wrong when written:
`page.getByRole('listitem')` selected the todo rows correctly, because the page held
exactly one list.

The query was never "the todos". It was "every list item on the page", which *happened* to
be the todos. Rendering a second `<ol>` changed the answer without changing a single line
of the tests, and the failures pointed at reordering, filtering and tagging — six files
away from the cause.

This is not a testing problem, it is a naming one. The todo list had no accessible name,
so there was no way to ask for it specifically; the test asked the only question the markup
could answer. Fixing the tests alone would have left the next feed to break them again.

**Give every repeated structure an accessible name, and scope every role query to one.**
`getByRole('list', { name: 'Todos' }).getByRole('listitem')` says what it means, survives
a neighbour appearing, and improves the page for a screen reader at the same time — the
markup change and the test fix are the same change.

The same trap applies to `getByRole('button')`, `getByRole('textbox')` and every other
role: an unscoped query is correct only for as long as the page stays sparse, and pages
never stay sparse. Related: [[L-026]] — enforcement that cannot tolerate correct change
decays; enforcement that is accidentally correct decays the same way, just later.
