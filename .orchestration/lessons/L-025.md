# A zone-less timestamp compared against now() is silently never due

`job.run_at` is `timestamp` without time zone, holding a UTC instant from a JavaScript
`Date`. The claim query said `where run_at <= now()`, and `now()` is `timestamptz`.

Postgres reconciles the two through the **server's** time zone. A job stored as UTC is
therefore not "due" unless the server happens to run in UTC — and the failure is total and
silent: the queue claims nothing, every job stays `pending`, and every test reports zero
processed with no error anywhere.

It cost a while because the symptom points at the claim query — `FOR UPDATE SKIP LOCKED`,
the `update ... where id = (select ...)` shape, PGlite compatibility — all of which were
fine. What settled it was selecting `run_at <= now() as due` and reading `false`.

Two fixes, and both are worth having:

- **The queue passes a `Date` parameter instead of calling `now()`.** Both sides are then
  the same type, and "now" becomes controllable — a test can run a job scheduled for
  tomorrow without waiting.
- **The schema was wrong repo-wide** and is now fixed by K-007: all 26 instant columns are
  `timestamp({ withTimezone: true })`, converted with an explicit
  `USING "col" AT TIME ZONE 'UTC'`. Without that clause Postgres reinterprets existing
  values as server-local and shifts every row with no error — a timezone conversion with an
  unstated source assumption is a data-loss bug wearing DDL's clothes.

  Enforced by `packages/db/src/schema/timezone.test.ts`, which fails on any zone-less
  column and runs the comparison under `Pacific/Auckland` to prove the answer no longer
  depends on where the server is.

The general shape: **`timestamp` is the default and `timestamptz` is almost always what you
want.** Getting it wrong costs nothing until something compares in SQL, and then it fails
in a way that looks like a bug in the comparison.
