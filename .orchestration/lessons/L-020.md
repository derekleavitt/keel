# The commit history contradicted the rule, and history is more persuasive

`.claude/rules/database.md` says feature branches must not run `pnpm db:generate`. But
T-02, T-03 and T-04 each landed a migration beside their feature — correctly, because that
work happened directly on `main` where generating *is* the integrator's job.

Nothing in those commits recorded the distinction. So from a feature branch the history
reads as three consecutive precedents for committing migrations, against one rule saying
not to. A cold agent building tags found the ambiguity and reported it precisely:

> The rule and the only two precedents disagree, which is why nobody had noticed.

It followed the rule. The next one might not, and would be reasonable either way.

**A rule contradicted by the repository's own history is already half-broken.** Precedent
is the strongest signal an agent has — it is concrete, it is in the codebase, and it
demonstrably passed review. An abstract rule loses that argument.

Two fixes: the rule now states the branch/integrator distinction explicitly and warns that
the history looks contradictory *and why*; and commits that generate migrations should say
they are doing so as the integrator.

**General rule:** when writing a rule, check whether the codebase already contradicts it.
If it does, either fix the code or explain the exception where the rule is stated —
otherwise the rule is decoration. Related: [[L-001]], where a file contradicted itself and
six agents read past it.
