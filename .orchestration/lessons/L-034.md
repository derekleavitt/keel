# A control that blocks local testing gets weakened unless you give it a hatch that cannot reach production

Webhook URLs are attacker-supplied and fetched **by the server**, so they are a
server-side request forgery surface by construction: without a check, any tenant can point
an endpoint at `http://169.254.169.254/` and have the application read its own cloud
credentials out to them.

The guard was easy. The problem it created was not: a developer's own receiver runs on
`127.0.0.1`, which is precisely what the guard blocks. With no way round it, the honest
outcome is that nobody exercises their webhook code until it is in production — and the
predictable *dishonest* outcome is that somebody eventually permits loopback
unconditionally "just for dev", shipping the hole to every deployment to make one
workflow convenient.

The resolution is an escape hatch with a hard ceiling:

- `WEBHOOK_ALLOW_PRIVATE_HOSTS`, off by default;
- the environment contract **refuses to parse** when it is set with `NODE_ENV=production`,
  so the application will not start rather than run with the guard disabled;
- the hatch does **not** unblock cloud metadata hostnames, which have no legitimate local
  use — leaving those reachable would make the hatch itself the vulnerability;
- `pnpm db:up` writes it into a fresh `.env`, so the working local default is the safe
  local default and nobody has to discover the variable to test their code.

**Refusing to start beats warning.** A warning is read once and then filtered; a parse
failure cannot be ignored, cannot be inherited from a copied `.env`, and cannot survive a
deploy script that forwards every variable it finds.

The general rule: when a security control makes a legitimate workflow impossible, that is a
design problem to solve, not a cost to absorb. An absorbed cost is paid later by whoever
quietly removes the control.

A second instance of the same principle appeared in the same task: reading the environment
to decide the URL policy can fail, and the fallback is the *strictest* policy rather than
the most convenient one — a control must never widen because configuration is missing.
