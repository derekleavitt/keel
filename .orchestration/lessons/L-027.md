# A file input inside a draggable row silently steals the drag

Adding an attachment control to a todo row broke reordering. `<input type="file">` is a
native drop target, so a drag landing anywhere near it never reached the row's handler —
no error, no console warning, the drop simply did nothing.

The failure was invisible in every direction that mattered: the drag *started* fine, the
row highlighted, the cursor changed, and nothing happened on release. Only a database check
showed the positions unchanged.

Two things came out of chasing it, and the second matters more:

**A row full of controls is an ambiguous thing to pick up.** Links, checkboxes, selects and
file inputs all have their own drag and click behaviour. A dedicated handle is not
decoration; it is the only unambiguous grab point.

**Drag-only reordering is an accessibility failure.** No keyboard path, no screen-reader
path, awkward on a phone. Chasing the drag bug was chasing the wrong problem: the fix was
explicit move-up/move-down buttons, which are the real interface, work everywhere, and are
the only thing a test can drive deterministically — HTML5 drag emulation varies between
browsers.

Drag is now the enhancement. The buttons are the feature.

Biome's `noStaticElementInteractions` then caught the handle being a `<span>` with
handlers, which is the same class of mistake one level down: an element with behaviour
needs a role, a name and focusability. It is a `<button>` now.
