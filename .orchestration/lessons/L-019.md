# Feature branches could not test the tables they had just written

`.claude/rules/database.md` forbids running `db:generate` on a feature branch — correctly,
per [[L-005]]. `packages/db/src/testing.ts` builds the test database by applying committed
migrations. Together those two true statements meant a branch that adds
`schema/<feature>.ts` had tables that existed in `schema` and in no migration, so
`createTestDatabase()` could not see them.

The query layer is where user scoping and cascade behaviour live. T-05's acceptance
criterion was "cascade direction asserted by a test, not a comment". Both were
unreachable on the branch that wrote them.

Nothing announced this. `select ... from "tag"` throwing reads as a broken test rather
than a missing mechanism, and both obvious ways out are wrong:

- **Commit the migration anyway.** Restores exactly the three-way conflict on
  `meta/_journal.json` that the rule exists to prevent. Two of the four committed
  migrations arrived this way, so the rule and the repository's own history disagree —
  which is how the contradiction stayed invisible.
- **Hand-write `CREATE TABLE` in the test.** `examples/notes` does this, legitimately, for
  a table that deliberately has no migration. Copied to a real feature it means the test
  asserts against DDL the test itself invented — a cascade test written that way proves
  the fixture is right and says nothing about the schema.

The fix derives the delta instead: `applyPendingSchema()` diffs the newest committed
snapshot against the live schema using the same drizzle-kit that `db:generate` uses, and
applies the statements to the test database. Nothing is written to `drizzle/`, the
integrator's migration is unchanged, and a branch tests its tables against real Postgres
with real foreign keys. It costs nothing when migrations are current: an
`information_schema` precheck decides, and drizzle-kit is imported only when something is
genuinely absent — so [[L-016]]'s once-per-process snapshot still holds.

**Enforcement.** `packages/db/src/testing.test.ts` asserts that every table and column in
`schema` is present in a fresh test database, discovering them rather than listing them.
Verified by disabling `applyPendingSchema()`: the guard fails naming the ten missing
columns, and passes with it restored.

**General rule:** when a rule forbids the only available route to a required outcome, the
rule is half a mechanism. Look for the missing half before routing around it — and note
that the repository's own history is evidence about which half is missing.
