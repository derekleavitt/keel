# Idempotency belongs in a constraint, not in a check

T-17 predicted "idempotency is the hard part and Keel says nothing about it. Expect a
lesson." The lesson turned out to be that it is only hard if you put it in the wrong place.

The instinct is a guard: before generating an occurrence, look for one; if it exists, skip.
That reads correctly and loses under exactly the conditions a job queue creates. Two workers
sweep at once, both read, both find nothing, both insert. `FOR UPDATE SKIP LOCKED` prevents
two workers claiming the same *job*, not two jobs racing on the same *row*, and a retry after
a partial failure is a second writer by another name.

The whole problem disappears into one partial unique index:

```sql
CREATE UNIQUE INDEX todo_occurrence_idx ON todo (recurrence_rule_id, occurrence_date)
  WHERE recurrence_rule_id IS NOT NULL;
```

with `.onConflictDoNothing()` on the insert. Running generation twice is a no-op. Running it
from three workers simultaneously is a no-op. There is no window, because there is no
read-then-write — the database decides, atomically, and it decides the same way under any
interleaving. The test that proves it fires three concurrent generations and asserts the
count.

**The general form: when "don't do this twice" matters, express it as a constraint on the
data rather than a decision in the code.** A check answers "was this true a moment ago"; a
constraint answers "is this true now", and only the second survives concurrency.

## The second half, which the constraint does not cover

Uniqueness stops *duplicates*. It does nothing about *resurrection*: delete a generated
todo, and the next sweep finds no conflicting row and helpfully recreates it. Every
recurring-task feature that has ever annoyed anybody does this.

That needs a watermark — `generated_through` — so generation resumes from the day after the
last one rather than re-expanding the series. Worth being precise about which mechanism does
which:

| Failure | Prevented by |
|---|---|
| the same occurrence inserted twice | the unique index |
| a deleted occurrence coming back | the watermark |

Neither substitutes for the other, and conflating them is how one of the two silently stops
working. Related: [[L-018]], where a default that existed only in JavaScript never reached
SQL — the same mistake of trusting application code with a guarantee the database should own.
