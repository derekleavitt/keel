# "Admin" is two different words, and storing them in one column hands every customer the keys

T-18 asked whether T-10's authorization model was too narrow for a second one layered on
top. It was not — but only because the second model was kept off it entirely.

An organization has roles: `owner`, `admin`, `member`. The obvious way to add staff access
is to extend that enum, or to treat `admin` of a designated internal organization as staff.
Both are catastrophic, for the same one-line reason:

> **Every customer can create an organization, and is automatically its owner.**

So any role expressed through membership is a role every customer can grant themselves.
"Admin of my own workspace" and "may read every workspace" share a word and nothing else.

They are separate axes and get separate storage: `membership.role` for tenancy, a
`platform_admin` table for staff. A row in that table cannot be created by anything a
request can reach — the only path is `pnpm admin:grant`, which needs shell access to the
deployment, and that is deliberately the level of access the capability is worth.

## The gate goes in the layout, not the page

`/admin/jobs` had existed since T-12, checking only that the caller was signed in. Every
customer could read every tenant's failing jobs, payloads included. The comment in that file
said role-gating would arrive with T-18 — an honest note that does nothing.

The fix is not to add a check to that page but to put one in `app/admin/layout.tsx`, which
covers every route beneath it. A per-page check is one page away from being forgotten, and
the page somebody forgets is the one that crosses tenants — silently, looking like a working
feature.

**404, not 403.** A 403 confirms the area exists and the reader is merely not allowed, which
tells an attacker where to spend their time. Same reasoning that makes another tenant's list
a 404 in the public API.

## A support tool the customer cannot audit is a back door

Staff actions go in `admin_action` — which is not `audit_entry`, because a tenant's log is
scoped by `organization_id` and that scoping is exactly what makes it safe to show a
customer. A platform action often has no tenant at all, and making that column nullable
would weaken the guarantee the tenant log depends on.

When an action *does* name a tenant it is written to **both**, attributed to the staff
member's real email. "Someone at the vendor looked at your account" is a worse answer than a
name, and a log only the vendor can read is not the same promise as one the customer can.

Reads are logged, not just writes. Support mostly looks at things, and "who opened this
account" is the question that actually gets asked.
